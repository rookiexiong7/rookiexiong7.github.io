## 1. Motivation：三维程序能运行，还需要知道它是否构造了正确的世界

文本生成网格或图像，可以快速得到一个看起来合理的三维结果，但最终产物通常不容易修改、组合和检查。用代码构造三维内容则保留了对象、尺寸、材质、关节、相机和动画的生成过程：用户可以改变参数，重新执行程序，或查询某个部件为何出现在当前位置。

问题是，三维编码并不只是一种语言或一种任务。静态物体可能用 Blender Python、CadQuery 或 OpenSCAD 构建；可动机构还需要 URDF 关节、轴和限位；场景与图形效果又可能落在 Three.js、GLSL 或 OpenGL 中。现有数据和 Agent 工作流通常只覆盖其中一部分，训练语料、执行环境、检查工具和评价协议彼此分散。

更困难的是，**程序成功执行不是三维内容正确的充分条件**。一张椅子可以被正常渲染，但椅腿没有接触座面；一扇门在静止姿态看起来完整，打开后却与门框穿插；一个 shader 能编译，却没有满足提示中的时序效果。若数据只按“能否运行”过滤，模型会学到语法，却未必学会空间结构。

3DCodeVerse 因此不是单一生成模型，而是一套研究生态：3DCodeVerse-2M 提供跨运行时的可执行程序语料；3DCodeVerse Harness 负责规划、并行构建、执行和自动修复；相同的执行记录又能形成监督微调与偏好学习数据。核心目标，是把三维代码的**生成、验证、修订和再训练**接成闭环。

## 2. Insight：执行、测量与视觉判断应当相互约束

### 2.1 “能编译”与“构造正确”是两层目标

普通代码生成常用单元测试判断输出是否正确；开放式三维内容却很少有唯一答案。执行成功只能排除语法、依赖和运行时错误，无法判断部件是否缺失、比例是否合理、接触是否成立或外观是否符合描述。

3DCodeVerse 将检查拆成三个层次。执行日志回答程序能否产生 artifact；空间工具测量包围盒、距离、接触、碰撞和运动学；视觉语言模型再根据多视角渲染评价语义、细节、材质与整体观感。三者覆盖的错误不同，不能由单一裁判替代。

### 2.2 确定性测量需要约束视觉裁判

视觉裁判擅长发现“龙鳞像圆顶按钮”一类感知问题，却可能从某个视角误判连接或碰撞。空间工具则能报告“部件相互穿透 3.2 mm”，但无法判断造型是否符合“东方龙”的风格。

论文让确定性检查对评分施加上限，并在测量明确反驳某个视觉缺陷时否决该判断。裁判先陈述可见证据，再给出分项分数；生成器的推理过程不会提供给裁判。这不是让 VLM 变成几何求解器，而是把它限制在适合感知判断的范围内。

### 2.3 生成轨迹本身可以成为训练数据

一次 Harness 运行会留下初始程序、构建失败、空间违规、视觉缺陷、局部修复和最终候选。成功与失败程序可用于执行偏好，几何较好与较差的候选可用于形状偏好，反复不终止与简洁有效的输出又能形成终止偏好。

这使 Harness 同时成为推理系统与数据引擎。不过，自动反馈中的偏差也会进入后续数据：如果评分规则遗漏某类错误，模型可能学会优化代理指标，而不是三维内容本身。因此，闭环的价值取决于验证信号是否独立、互补并可审计。

### 2.4 “2M”不是 200 万个独立程序

论文中的几个数据规模使用不同计数单位，必须分开理解：

| 层级 | 数量 | 含义 |
| --- | ---: | --- |
| 唯一可执行程序目录 | 269,597 | 跨 CadQuery、Blender、OpenSCAD、URDF、Three.js 与 GLSL 的独立程序 |
| 基准训练对 | 768,596 | 去重后的 prompt–code 训练切分，共 891M tokens |
| 统一文本导出 | 2,028,286 | 一个程序可展开为多种描述视角，multi-pass shader 还会拆成 pass 级目标 |

因此，3DCodeVerse-2M 的“2M”对应统一文本导出的行数，不等于 200 万种独立几何或 200 万个独立程序。这个区别也会影响对数据多样性的判断。

## 3. Method：从异构程序语料到可自动修订的多 Agent Harness

### 3.1 把三维编码写成可执行任务

论文将条件记为 $c$，其中包含文本请求和可选参考图像；程序 $f$ 在声明的环境 $e$ 中运行：

$$
(a,\ell)=\mathcal E_e(f),\qquad x=\mathbb I[a\neq\bot].
$$

$a$ 是网格、可动资产、场景或动画，$\ell$ 是执行反馈，$x$ 只表示程序是否成功产生结果。当存在参考 artifact $a^\star$ 时，可以计算 $D(a,a^\star)$；没有唯一参考时，则依靠空间测量与渲染结果 $o=\mathcal R(a)$ 检查条件是否满足。

单次模型直接生成 $f^{(0)}$。编码 Agent 则像开发者一样，根据此前的代码、日志和渲染继续修改：

$$
f^{(t)}=\pi\!\left(c,\{f^{(k)},\ell^{(k)},o^{(k)}\}_{k<t};e\right).
$$

这里的关键不是增加自由形式的“反思”，而是让每轮修订获得可定位到部件与数值的证据。

### 3.2 3DCodeVerse-2M 怎样构建？

[![3DCodeVerse-2M 从公开数据和 Harness 生成结果出发，通过 Agent 与检查工具形成跨代码环境的数据](/blog/assets/3dcodeverse/dataset.webp)](/blog/assets/3dcodeverse/dataset.webp)

*图 2. 数据来源、Agentic Data Curation 与最终代码类型。图源：原论文 Figure 2。*

数据管线包含收集、转换和 Agent 生成三类来源。原始项目如果依赖专用 API，Agent 会内联必要例程、补齐资源并改写成可在指定运行时独立执行的程序；DeepCAD 序列则由确定性编译器转换为 CadQuery。每条记录保留代码、运行环境、描述、来源、许可与可用的验证结果，图像、网格和视频只在对应来源能够提供时关联。

唯一程序目录的分布并不均衡。DeepCAD 转换的 CadQuery 程序占 47.55%，Shadertoy GLSL 占 44.50%，两者合计 92.05%；可动物体、场景和 Agent 编写程序位于更小的长尾中。数据的“跨环境”覆盖是真实的，但不能据 2M 行数推断各任务拥有均衡规模。

转换过程也保留了可核对指标。例如，178,238 条 DeepCAD 原始序列最终得到 128,201 个去除精确几何重复后的唯一可执行程序；平均 voxel IoU 为 0.985，96.9% 超过 0.90。上游切分中有 3,230 组重复几何跨越训练与测试，论文使用向量和网格去重消除这条 CAD 血缘中的交叉切分泄漏。Harness 另外产生 15,704 个通过执行验证并带有质量层级、checklist 和 gate 记录的 bootstrap 程序。

许可也不是一个统一标签可以概括的。数据集整体采用 CC-BY-NC-SA-4.0，但论文明确说明，来源条目的更严格许可仍然优先。复用者需要读取样本级 provenance 和 license，而不能只看总数据集许可。

### 3.3 DAG 怎样组织多 Agent 构建？

[![3DCodeVerse Harness 用 DAG 分解构建任务，再通过执行、测量、渲染和视觉裁判循环修订](/blog/assets/3dcodeverse/harness.webp)](/blog/assets/3dcodeverse/harness.webp)

*图 3. 3DCodeVerse Harness 的规划、构建与自动修订循环。图源：原论文 Figure 3。*

Planner 先从条件 $c$ 生成结构计划 $P$，明确目标部件、尺寸、材质、空间关系和验收条件。Harness 再把计划转成 DAG $G=(V,E)$：节点是编码或装配任务，边表示依赖关系。互不依赖的节点拥有明确的文件写入范围，可以由多个子 Agent 并行完成；装配节点只在前置任务通过后整合结果。

文件所有权不只是为了提速。三维项目往往包含几何、材质、场景入口和 URDF 等多份文件，如果多个 Agent 无边界地修改同一上下文，局部修复容易破坏其他部分。DAG 将问题分解为相对独立的子树，也限制单个会话不断增长的历史。

### 3.4 每轮反馈怎样变成局部修复？

每轮按优先级收集三种反馈：

1. **执行反馈**：构建或运行失败时只返回日志，不对不存在的 artifact 做视觉评价。
2. **测量反馈**：检查尺寸、接触、碰撞、运动学和放置关系，返回对应部件与数值修正提示。
3. **视觉反馈**：VLM 根据请求、计划、验收条件、多视角渲染和测量结果，输出缺陷证据、分项分数与修订建议。

这些反馈被编译成去重、排序后的修复任务 $\Delta^{(t)}$，Fix Agent 生成 $f^{(t+1)}$。最后交付评分最高的有效轮次，而不是默认接受最后一次修改。开发阶段还交替固定生成流程优化裁判、再固定裁判优化 Harness，以减少评分抖动和与测量证据冲突的判断。

论文的系统消融给出几条具体工程经验：遇到退化的运动学计划时，回到原始请求并带上违反的 schema 规则重新采样，比在污染上下文中继续补丁更可靠；语义上的“检测到碰撞”不能作为工具传输错误，否则会触发无意义重试；诊断 payload 和会话深度需要设界，避免图像与历史让成本超线性增长。

## 4. Experiments：Harness 提高质量，但也显著增加计算与评审开销

### 4.1 固定骨干后，Harness 通常优于原生工作流

Harness 实验覆盖静态物体、可动物体、场景和程序化图形。Human Preference 是匿名成对比较中的胜率，平局各计半分；Judge Score 由冻结的 Gemini 3.1 Pro 评审管线给出，失败程序记零；论文还报告 VLM Preference 与 SigLIP-2 文本–图像相似度。

[![3DCodeVerse Harness 与相同骨干模型原生工作流在四类三维编码任务上的比较](/blog/assets/3dcodeverse/results.webp)](/blog/assets/3dcodeverse/results.webp)

*图 4. 四类任务中的人类偏好与 Judge Score；斜纹为原生 Harness，实色为 3DCodeVerse Harness。图源：原论文 Figure 4。*

以静态物体为例，同一骨干下的结果如下；Judge Score 四舍五入到整数：

| 骨干与对照 | 原生流程 Human Pref. | 3DCodeVerse Human Pref. | 原生 Judge | 3DCodeVerse Judge |
| --- | ---: | ---: | ---: | ---: |
| Gemini 3.8 Flash / Gemini CLI | 13 | 87 | 61 | 87 |
| Claude Opus 5.5 / Claude Code | 21 | 79 | 77 | 88 |
| GPT-6 Astra / Codex | 31 | 69 | 76 | 88 |
| GPT-6 Luna / Codex | 11 | 89 | 64 | 86 |
| Claude Opus 5.5 / Claude Design | 10 | 90 | 37 | 88 |

最后一行是摘要所说的 90% 胜率：Claude Design 与 3DCodeVerse Harness 都使用 Claude Opus 5.5。它说明在这套提示、渲染和成对评价协议下，工作流对结果影响很大；它不是 90% 的绝对任务成功率，也不能推广为对所有 3D 工具的统一胜率。

实验的样本边界也值得注意。物体提示池共有 100 条，但附录说明，Gemini Flash 和 Claude Opus 的主要比较使用 60 条子集，GPT-6 Astra 与 Luna 使用按难度平衡的 30 条子集。图中不同骨干的柱子并非都在完全相同的 100 条提示上形成一张总榜单。场景和图形各有 50 条提示，其他附加实验还使用更小的 hard-prompt 子集。

### 4.2 数据微调首先改善可执行性，几何保真度仍需单独检查

开放模型实验在 805 个固定任务上评价六种环境：3DCodeBench 212 条、Blender 103 条、CadQuery 200 条、OpenSCAD 50 条、GLSL 200 条、Three.js 40 条。模型以 $T=0.7$、单个随机种子生成，输出在固定运行时实际执行。下表为原论文 Table 2 的执行率：

| 模型 | 3DCodeBench | Blender | CadQuery | OpenSCAD | GLSL | Three.js |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3.5-9B | 0.0 | 1.9 | 10.5 | 50.0 | 33.0 | 72.5 |
| + SFT | 84.9 | 90.3 | 98.5 | 86.0 | 56.0 | 74.5 |
| Qwen3.8-27B | 51.9 | 74.8 | 65.5 | 80.0 | 57.0 | 72.5 |
| + SFT + DPO | 92.9 | 93.2 | 98.5 | 90.0 | 71.5 | 92.5 |

提升很大，但“程序运行了”仍不等于“几何匹配”。在 3DCodeBench 上，9B 的无条件 F-score（阈值 0.05）从 0 增至 0.317，27B 从 0.214 增至 0.374；Blender 上分别从 0.008 增至 0.693、从 0.439 增至 0.798。CadQuery 的 9B 执行率虽达到 98.5%，同一 F-score 只有 0.308。执行率更像第一道门，形状指标才继续衡量通过门后的结果。

两组模型也不是完全相同的处理：9B 主结果是 SFT，27B 主结果包含 SFT 与 execution DPO，不能把 27B 的全部差值只归因于数据监督。主表又只使用一个采样种子，适合说明固定协议下的幅度，不足以刻画生成方差。

### 4.3 自动闭环的收益来自更多推理，也付出了更多成本

在 60 条物体提示上，Gemini 3.8 Flash 原生单次生成的估算成本为每项 0.035 美元，执行率 93.3%，Judge Score 61.3；接入 Harness 后成本为 3.312 美元，执行率 100%，Judge Score 86.6。Harness 平均读取约 20.8M input tokens，其中 93.9% 来自低价 prompt cache，并输出约 234.9K tokens。缓存让成本可控，却没有消除计算量。

更强骨干同样存在质量—成本取舍。在 8–11 条 hard prompts 上，GPT-6 Sol 从 one-shot 的 0.603 分提升到 Harness 的 0.758 分，估算成本从 0.29 美元增至 6.72 美元；Gemini Flash 从 0.146 增至 0.625，成本从 0.04 美元增至 2.41 美元。这些不是与主图相同的样本或评分设置，但共同说明：闭环验证是 inference-time scaling，不是免费的架构增益。

论文的组件级遥测也表明，系统工程可以减少浪费：

| 机制 | 直接指标 | 调整前 | 调整后 |
| --- | --- | ---: | ---: |
| 计划失败后重采样 | 无效计划，560 次调用 | 4.7% | 0.7% |
| verdict 与传输错误分离 | 冗余重试，3,677 次调用 | 26.6% | 1.3% |
| 限制诊断 payload | 每次请求未缓存 tokens，5,194 次请求 | 38,521 | 13,480 |
| 缩短会话范围 | 1,063 个会话的 tokens / 成本 | 完整深度 | −68% / −55% |

这些消融测的是各机制对应的操作指标，并非都直接证明最终三维质量同比上升。它们更适合作为构建长链路编码 Agent 的工程证据。

### 4.4 现有证据还没有覆盖什么？

第一，数据规模由 CAD 与 shader 主导。可动物体、复杂场景和 Agent 生成程序虽然存在，但唯一程序分布远小于前两类。跨方言训练的迁移结果令人鼓舞，仍不能据此认为各类三维世界都获得了同等覆盖。

第二，独立评测会从头构建产物，隐藏内部计划与修订历史，用三次 Gemini 3.1 Pro 判断、确定性几何上限、SigLIP-2 和盲测人类偏好交叉验证。这减少了生成器直接迎合内部裁判的风险，但评价 rubrics、视角选择和提示分布仍由同一研究体系设计。人类偏好评价关注渲染结果，并没有直接测量用户编辑代码的效率、参数可控性或长期维护成本。

第三，静态渲染质量、可执行关节和物理上可靠的世界模型是不同目标。论文的机器人实验只有两个资产、两种初态与三类控制序列形成的 12 个 case；视频应用主要展示代码渲染对生成模型的条件控制。它们证明了代码表示的潜在用途，还不足以建立大规模机器人策略学习或真实物理预测的结论。

最后，自动验证只能检查已经形式化的约束。没有被 rubric、测量工具或视角暴露的问题仍可能漏过。扩展这套生态时，最重要的不是继续增加一个总分，而是记录每条结论来自执行、几何测量、视觉判断还是人类评价，让失败可以追溯。

## 5. Conclusion

3DCodeVerse 最有价值的贡献，是把三维代码从“模型输出的一段脚本”提升为一套可运行、可测量、可修订的数据生产过程。异构程序被整理成自包含项目；复杂资产由 DAG 分解并装配；执行、空间和视觉反馈分别处理不同错误；修订轨迹又反过来训练开放模型。

实验清楚支持两个结论：3DCodeVerse-2M 的监督显著改善多种运行时上的代码可执行性，3DCodeVerse Harness 也能在固定骨干下明显提高人类偏好与自动评分。但这些收益伴随更高推理成本，且 2M 行导出不能等同于 2M 个独立世界；自动评审、数据长尾和物理有效性仍是主要边界。

更进一步的验证，应当在固定计算预算下比较不同反馈组合，并加入真实编辑任务：用户能否快速改变部件、关节和场景约束，修改后是否仍能通过跨视角与动态检查。只有当代码既能生成好看的结果，又能在持续修改中保持结构正确，它才真正成为可复用的三维世界表示。
